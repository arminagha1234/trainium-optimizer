# NKI Kernel Performance Guide — banked (Opt #1–#10 + thresholds)

Distilled from the official AWS guide:
<https://awsdocs-neuron.readthedocs-hosted.com/en/latest/nki/deep-dives/nki_perf_guide.html>
(applies to Trn2 / Trn3). This is the AUTHORITATIVE bank of the guide's numbered
optimizations + threshold bars; our broader applied notes live in
[`nki-optimization-playbook.md`](./nki-optimization-playbook.md). The framework
wires this via `perf_hints.py` (symptom → Opt) and the threshold constants in
`neuron_profile.py` / `roofline.py`.

## Why / where a hand-written kernel beats the compiler

The guide never claims hand-written beats the compiler — it shows *which levers
are whose*, and that is the whole answer to "we can't beat the compiler":

- **The compiler already applies the COARSE levers** automatically — Opt #1/#2
  (tiling, loop-fusion spill management: "spill/reload DMAs are generated by the
  Neuron Compiler by analyzing SBUF usage") and Opt #9 (DMA sizing). That is why
  a hand GEMM / elementwise / norm loses: those are near-SOL because the compiler
  nails the automatic levers.
- **The author controls the levers the compiler can't infer:** algorithm-level
  fusion (keeping the flash `[S,S]` scores out of HBM), engine mapping, layout /
  transpose choices, and the low-level `nki.isa` instruction tricks (Opt #6/#7/
  #5b/#8). **You beat the compiler where it lacks information you have** — the
  compiler-weak families (scan / long-context attention) *and* these `isa`-level
  tricks even on regular ops.
- **The process that wins is profile-driven iteration:** author → profile →
  diagnose the ONE dominant bottleneck → apply its specific Opt → re-measure.
  The compiler picks one schedule; we can iterate against the real profile. That
  loop is `kernel_perf.KernelPerfLoop` + `perf_hints`.

## Goal: end compute-bound OR memory-bound, at the right bar

| State | "good" bar | our constant |
|---|---|---|
| Compute-bound (engine active near 100%) | **≥ 90%** | `roofline.COMPUTE_BOUND_GOOD_SOL`, `neuron_profile.COMPUTE_GOOD` |
| Memory-bound (MBU near 100%) | **≥ 60%** | `roofline.MEMORY_BOUND_GOOD_SOL`, `neuron_profile.MBU_GOOD` |
| Matmul MFU | **~100% target, ≥ 90% good** | `neuron_profile.MFU_GOOD` |
| Elements / partition | **≥ 128** | `roofline.MIN_ELEMS_PER_PARTITION` |
| DMA transfer size | **≥ 32 KiB** | `roofline.IDEAL_DMA_TRANSFER_KIB`, `neuron_profile.DMA_IDEAL_KIB` |
| DMA free-dim | **~1024** (beyond → diminishing return) | `roofline.IDEAL_DMA_FREE_DIM` |
| Spill traffic / SBUF traffic | **> 30% → investigate** | `neuron_profile.SPILL_INVESTIGATE` |
| Systolic array | 128×128; TensorE > 90% of core FLOPS | — |
| Static instruction overhead | **~100 cycles** (amortize with big free tiles) | — |

## Workflow (order matters)

1. **First maximize arithmetic intensity** — Opt #1 (avoid input reload) + Opt #2
   (fuse to cut spills). These trade off (caching ↑ SBUF pressure → its own spills).
2. **Then check the profile** — `engine_active_time_percent` / `dma_active_time_percent`
   in the Summary tab → compute- or DMA-dominated?
3. **Compute-dominated →** reduce idle gaps (Opt #3/#4) then engine efficiency (#5–#8).
4. **DMA-dominated →** data-movement efficiency (Opt #9/#10).

**Diagnosis by semaphore wait:** for each idle gap, inspect the first instruction
after it. Waiting on a compute-engine semaphore (Vector/Scalar/GpSimd/Tensor) →
Opt #3 (pipeline). Waiting on a `q`-prefixed semaphore (`qSyncIO0` load,
`qSyncSpillReload0` spill) → Opt #4 (overlap load/compute).

## The 10 optimizations (symptom → fix)

| Opt | Symptom | Fix | ~gain |
|---|---|---|---|
| **#1** | repeated `nl.load` of the same tensor | keep reused data resident in SBUF (temporal locality) | — |
| **#2** | spill traffic > 30% of SBUF traffic | fuse producer→consumer; declare buffers INSIDE the inner loop | — |
| **#3** | idle gap waits on a compute-engine semaphore | slice into tiles, pipeline across PE/Scalar/Vector/GpSimd | — |
| **#4** | idle gap waits on a `q`-semaphore (load/spill) | double-buffer: tile n+1 DMA overlaps tile n compute | — |
| **#5a** | many back-to-back tiny (1-elem/partition) instructions | big free-dim tiles (≥128); `nisa.tensor_tensor_scan` for scans | — |
| **#5b** | instruction spans < 128 partitions (two serial reduces) | pack onto disjoint partitions 0:63 / 64:127 → one 128-wide op | **2×** |
| **#6** | multiply→add→exp as separate ops (multi-pass) | one `nisa.activation(exp, data, bias, scale)` — touch data once | **3×** |
| **#7** | short-dim matmul (matrix-vector / bs=1 decode), low MFU | map the SHORT tensor to MOVING, LARGE to STATIONARY (fast LoadStationary); `A@B=(Bᵀ@Aᵀ)ᵀ` | **up to 4×** |
| **#8** | an intermediate transpose only to satisfy a layout | swap stationary/moving so output layout matches next op; or move reduce to the native-layout engine | — |
| **#9** | DMA-bound, small transfers (< 32 KiB) | widen both dims, transfer ≥ 32 KiB, free-dim ~1024; all 16 DMA engines busy | — |
| **#10** | low-bandwidth `nl.load_transpose2d` | replace with `nl.load()` + tiled `nisa.nc_transpose()` (when memory-bound & TensorE idle) | — |

## Worked examples (guide's own)

- **Flash attention** (#2/#3/#6): naïve matmul→softmax→matmul overflows SBUF with
  the `[S,S]` intermediate at multi-thousand context; fuse + pipeline (exp→ScalarE,
  sum→VectorE, scale→ScalarE, causal mask→GpSimdE, matmuls→TensorE).
- **Mamba prefix-sum** (#5a): `seq_len` back-to-back 1-elem `tensor_scalar` ops
  (189 ns / 264 cyc overhead vs 1 useful cyc) → `nisa.tensor_tensor_scan`.
- **Partition vectorization** (#5b): two 64-partition reduces → disjoint-partition
  pack + one 128-wide `tensor_reduce` = 2×.
- **Instruction combine** (#6): 3-op exp chain → one `nisa.activation` = 3×.
- **Matrix-vector** (#7): `[1,128]×[128,128]` short-stationary (MM every ~128 cyc)
  vs short-moving (LS ~32 cyc, MM ~64 cyc) → up to 4×. Autoregressive decode.
- **LayerNorm / RMSNorm** (#8): map the weight to MOVING so the output free-dim
  matches `bn_stats` (skip the transpose); for `linear→RMSnorm→linear` keep weight
  stationary and reduce cross-partition on TensorE.

## How this is wired into the framework

- `perf_hints.py` — symptom haystack (bottleneck + profile-threshold tokens + op
  shape) → the specific Opt #, prepended to the perf re-author guidance.
- `nki_knowledge.TECHNIQUES` — `fast-weight-load` (#7), `partition-vectorize`
  (#5b), `tensor-tensor-scan` (#5a), `transpose-swap-for-layout` (#8).
- `neuron_profile.py` — parses MFU/MBU/spill/DMA-size, emits `perf_symptoms`
  tokens; `roofline.py` — per-bottleneck `good_sol_bar` (90%/60%).
- `kernel_perf.KernelPerfLoop.diagnose` — routes to `specific_guidance`
  (perf_hints) and converges against the per-bottleneck bar.

## Static-addressing / gather-as-matmul (the UniVR win — a new op class)

The UniVR shutter-unroll optimization is our thesis on a new op family: it turned
a compiler-weak **indirect-DMA** op (`F.interpolate` bilinear) into compiler-strong
TensorE work, **13× cumulative**.

- **GpSimd-bound is a first-class bottleneck.** An indirect/dynamic gather runs on
  GpSimd's programmable procs + its slow integrated DMA (153 GB/s/dir) and
  serializes while TensorE idles. UniVR measured GpSimd 71% → 33.8%, TensorE 2.4%
  → 21.9% → 67%. `neuron_profile` now emits `gpsimd_bound` (distinct from
  `single_engine`); `perf_hints` routes it to the two levers below.
- **Lever 1 — host-static-addressing** (`nki_knowledge` technique): if sampling
  indices are data-independent at trace time, compute them on the host and bake as
  compile-time constants → every DMA static-addressed (758.9 → 106 ms, 7×).
- **Lever 2 — gather-as-matmul** (`nki_knowledge` technique + `indirect_gather` op
  family in `opportunity.py`): a fixed-pattern gather/interpolate/upsample is
  linear → `out = W @ x` with a precomputed mostly-zero weight matrix, run on
  TensorE (107 → 55.6 ms, 1.92×, TensorE → 67% busiest).
- **Honest limit:** STATIC access patterns only. Data-dependent gathers (KV-cache
  paging, MoE token dispatch) can't bake indices as constants — do NOT apply there.
- **Multi-core lesson (48xl playbook):** per-core tile ownership + halo; collect
  results in HBM over NeuronLink, never round-trip host memory (98 → 14.5 ms, 6.8×).
  And sequence the search "maximize single-core FLOPs first, THEN re-derive tile
  size + core count" — a faster tile changes both.
- **Reporting discipline:** report a domain fidelity metric (PSNR / max-error, e.g.
  UniVR's 97.22 dB / 0.73 LSB) *and* a GPU baseline (trn3 268 ms vs L40S 351 ms)
  next to the speed number — for `task_eval` and the leaderboard.
